# Самопроверка VPd03

<details>
<summary>1. Почему ключ нельзя хранить в коде?</summary>

Код попадает в git, на GitHub, в архивы и скриншоты. Ключ в коде утекает вместе
с ним, а история git хранит старые версии файла. Последствия — чужие запросы
за ваш счёт, исчерпанные лимиты, блокировка. Поэтому ключ живёт только в `.env`,
а `.env` — в `.gitignore`.
</details>

<details>
<summary>2. Что делает связка `load_dotenv()` и `os.getenv("API_KEY")`?</summary>

`load_dotenv()` читает `.env` и кладёт пары «имя=значение» в переменные окружения
процесса. `os.getenv("API_KEY")` достаёт значение по имени. Имя переменной в `.env`
и в коде должно совпадать, иначе вернётся `None`.
</details>

<details>
<summary>3. Зачем в проекте `.env.example`, если есть `.env`?</summary>

`.env` — секрет, в git его нет. `.env.example` — шаблон без значений: показывает,
какие переменные нужны. По нему новый человек создаёт свой `.env` и вставляет свой ключ.
</details>

<details>
<summary>4. Почему погоду нельзя запросить по названию города?</summary>

Current Weather API принимает координаты. Название сначала переводят в `lat`/`lon`
через Geocoding API, а уже потом запрашивают погоду. Отсюда две функции:
`get_coordinates` и `get_weather_by_coordinates`.
</details>

<details>
<summary>5. Что вернёт геокодинг, если город не найден?</summary>

HTTP 200 и пустой массив `[]`. Ошибка не приходит — её нужно распознать самому
по пустому списку. Поэтому проверки только `status_code == 200` недостаточно.
</details>

<details>
<summary>6. Зачем `units=metric` и `lang=ru`?</summary>

Без `units` температура приходит в кельвинах: 281 — это не -8 °C. `units=metric` даёт
°C и м/с. `lang=ru` просит описание погоды на русском («пасмурно» вместо «overcast clouds»).
</details>

<details>
<summary>7. Почему геокодинг вызывается с `limit=1`?</summary>

Названия повторяются: Приморск есть в Ленинградской области и в Дагестане.
API сортирует совпадения по популярности, поэтому достаточно первого. `limit=1`
ограничивает ответ одним элементом, а `data[0]` даёт «главный» город.
</details>

<details>
<summary>8. Что означают `429` и `401` и почему реакция разная?</summary>

`401` — ключ неверный или ещё не активировался. Повторять бессмысленно, нужен
правильный ключ. `429` — превышен лимит запросов; через секунды запрос может пройти,
поэтому делаем до трёх повторов с паузами 1, 2, 4 с. То же для `5xx` и обрыва сети.
</details>

<details>
<summary>9. Почему кэш предлагается только на 3 часа?</summary>

Погода быстро устаревает: данные трёхчасовой давности ещё дают представление
о погоде, суточной — уже нет. Возраст считается по `fetched_at` из метаданных,
а не по времени изменения файла.
</details>

<details>
<summary>10. Что хранится в `weather_cache.json`?</summary>

Последний успешный ответ API и метаданные: `city`, `lat`, `lon`, `fetched_at`
(время получения, ISO 8601 UTC) и `weather` — сам ответ. Город и координаты нужны,
чтобы показать, к чему относятся данные, `fetched_at` — чтобы посчитать возраст.
</details>

<details>
<summary>11. Почему функции возвращают `dict`, а печатает CLI?</summary>

Функция с `print` неудобна для тестов и повторного использования. `get_coordinates`
возвращает координаты, `get_weather_by_coordinates` — словарь; решение, что и как
показать, принимает CLI. Тесты подменяют `requests` и проверяют данные, а не текст в консоли.
</details>

<details>
<summary>12. Как проверить, что ключ не попал в репозиторий?</summary>

`git ls-files` не должен показывать `.env` и `venv/`; `git status` — чистый
по секретам; в коде не должно быть строки с самим ключом. Если ключ всё же
закоммичен — ключ перевыпускают: удаление коммита не помогает, история остаётся у клонов.
</details>
